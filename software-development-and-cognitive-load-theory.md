# Software Development and Cognitive Load Theory

With the increasing use of AI in software development workflows, a common complaint among engineers is the overwhelming amount of content we are expected to read. AI-generated README files, code comments, pull request descriptions, and code reviews often resemble essays. Even when developers provide precise prompts, LLMs tend to produce significantly more text than humans would naturally write.

The challenge is not merely the volume of information, but the cognitive effort required to process it. This information overload can contribute to developer fatigue and may be partly explained by Cognitive Load Theory, developed by John Sweller at UNSW in the late 1980s. The theory is grounded in the architecture of **working memory**, the workspace where "learning, thinking, and problem-solving" actually happen. This working memory can hold only a very small number of elements at a time, and unrehearsed information decays from it in about 20 seconds, a limit lightly explored in St Andrew's Cathedral School's talk [*In Conversation: Cognitive Load Theory*](https://www.youtube.com/watch?v=srkgXMHdaUs).

Now consider a common scenario: you request an AI code review. The pull request review comes back with a large number of verbose comments. Although some observations may be valuable, a reader cannot pre-filter what is irrelevant before reading it. Every extra sentence, caveat, or restated fact consumes working memory that should be focused on the real decisions: Should I approve this? Is this correct? Does it handle the edge case?

Sweller identifies this as one of the central failure modes of information design, calling it the redundancy effect: information that adds little or no instructional value still consumes cognitive resources.

Another emerging phenomenon is what some engineers colloquially call the "meat-proxy" problem. A human author uses an AI model to generate code, while a human reviewer relies on another AI model to review it. The author then uses AI again to address the review comments and generate responses.
When this pattern emerges, we risk becoming intermediaries between models rather than active participants in the technical discussion. The process can also generate such large volumes of content that both humans and AI agents experience context overload. This can result in low-quality or otherwise undesirable changes being merged simply because scrutiny degrades as review volume increases. One could even view the exploitation of reviewer exhaustion as a form of "memory overload attack", where excessive content reduces the likelihood that important issues are identified and challenged.

With that in mind, my main takeaway is simple: **we must be concise**. Content is cheap to produce but extremely expensive to consume and comprehend. **Working memory is precious.**
Every sentence in a comment, README, or review is a claim on a fixed, tiny budget for the human *and* for the model reasoning over it.

Another concept from Sweller that resonates strongly with software development is the split-attention effect. In education, it can be illustrated by presenting a diagram alongside text that conveys essentially the same information. Attention naturally shifts back and forth between the two representations: the reader looks at the diagram to understand the text and then returns to the text to interpret the diagram. That context switching consumes working memory.
For software development, I'd stretch the concept beyond its original educational context and argue that documentation should live as close as possible to the code it describes. When knowledge is distributed across multiple repositories, wikis, design documents, and chat threads, the cognitive burden increases. Every repository should instead act as a small, scoped semantic container: co-located with the code it describes and carrying only the context required for a human or a model to reason effectively about that component without pulling in unnecessary information from elsewhere.
